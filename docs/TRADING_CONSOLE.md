# Trading console

Sentum provides an interactive terminal trading workstation for Paper and Binance Spot Testnet runtime modes. The console is backed by the same `DashboardState` used by the web dashboard, so runtime state is not duplicated between user interfaces.

## Start

```bash
./sentum paper
./sentum testnet BTCUSDT
```

The terminal UI starts automatically when stdout is attached to a TTY. For services, CI, redirected output, or headless operation use:

```bash
./sentum paper --no-tui
```

## Views

The console is organized around seven views selectable with keys `1` through `7`:

- **Market** — paper equity, realized/unrealized P/L, active position, stop/target, risk limits, market watch and recent trades.
- **Scanner** — ranked scanner candidates with current symbol context and returns.
- **Orders** — persisted order-state events including state, requested/executed quantity, fill price and source.
- **Trades** — completed trades, fees, net P/L, exit reasons and a compact equity curve.
- **Strategy** — active strategy, signal, confidence, signal explanation, risk decision and ensemble members/weights.
- **Models** — registered model lifecycle state and promotion history.
- **System** — collector/scanner/trader health, event throughput, queue/drop metrics, database size and runtime latency percentiles.

The Market view is intentionally trading-first. Parser, event-dispatch, decision and SQLite latency telemetry live in the System view instead of dominating the main screen.

## Terminal rendering

The interactive console uses the terminal alternate-screen buffer, similar to tools such as `htop` or `vim`. The normal shell scrollback is restored when the TUI exits.

Sentum clears the terminal only when the console starts, after a resize, or when a tab change requires a complete layout refresh. Normal runtime updates are rendered through a stateful frame buffer: the new frame is compared with the previous frame and only changed terminal rows are rewritten.

`DashboardState` maintains a generation counter. The TUI polls for input at a short interval but does not render when runtime state, cached repository data, terminal dimensions and local UI state are unchanged. Orders, trades, models and equity history retain their slower two-second refresh cadence.

This design minimizes terminal I/O and visible flicker, including over SSH, while keeping keyboard input responsive.

## Paper controls

Paper mode supports interactive runtime controls:

- `S` — cycle strategy presets.
- `A` — return to automatic scanner-driven symbol selection.
- `M` — enter a manual symbol and press Enter; Escape cancels.
- `P` — pause or resume new entries. Existing positions remain managed.
- `C` — request a manual Paper close through `SimulatedExecutionVenue`.
- `Ctrl+C` — begin a graceful Sentum shutdown.

Strategy and symbol changes are deferred while a position is open. They are applied only after the current position exits.

## Graceful shutdown

`Ctrl+C` does not terminate worker threads abruptly. Sentum switches from the trading workstation to a dedicated shutdown screen and reports the current cleanup step and overall progress.

Paper shutdown proceeds through the trader, market stream/database writer, runtime coordinator, scanner worker, final runtime-state update and dashboard shutdown. Buffered market data is allowed to flush before the process exits.

The runtime coordinator wait is interruptible, so shutdown no longer waits for the normal one-second refresh sleep to expire. In non-interactive/headless execution the same stages are emitted as plain log-style lines instead of ANSI redraws.

Normal shutdown and worker-error cleanup use the same stop signalling. Idle scanner, trader and logger workers receive the stop request even when they are entering a wait; cleanup does not depend on another market event or log message arriving.

## Strategy runtime

Paper trading uses the same `sentum::strategy::StrategyFactory` used by research and model workflows. Supported strategy types are:

- `momentum`
- `trend`
- `mean_reversion`
- `breakout`
- `multi_timeframe_trend`
- `ensemble`

The normal runtime strategy is configured in `config/config.json`. Example:

```json
{
  "strategy": {
    "type": "trend",
    "parameters": {
      "fast_period": 12,
      "slow_period": 26,
      "threshold": 0.001
    }
  }
}
```

The Strategy view reports the actual signal, aggregate confidence, signal reason and risk decision generated by the trading pipeline. For ensembles, member weights are shown; Sentum does not fabricate per-member confidence values that the strategy engine does not expose.

## Paper account

Paper trading uses a persistent simulated account rather than the authenticated Binance account balance. Configure it in `config/config.json`:

```json
{
  "paper": {
    "initialBalance": 10000.0,
    "statePath": "log/paper_account.json",
    "autoSymbol": true,
    "symbol": "",
    "modelDefinition": ""
  }
}
```

The account persists equity, realized P/L and closed-trade count across restarts. Position sizing uses the current simulated equity.

Only a missing state file starts a new account. An existing file must contain the original five fields: `currency`, `initial_balance`, `equity`, `realized_profit` and `closed_trades`; no schema-version migration is required. Currency and initial balance must match the current configuration. Balances and profit must be finite numbers, and the closed-trade count must be a nonnegative integer within the supported range. Malformed, incomplete, unreadable or incompatible state causes an explicit error and is left untouched. State files must be regular files; symbolic links and other file types are rejected. To start a separate account with another initial balance or currency, configure another `statePath`.

Use one writer per account path on a Linux filesystem that supports hard links, atomic rename, and file and directory `fsync`. Saves create a private, exclusively created temporary file in the state directory, write and synchronize its complete contents, retain the previous file, then atomically replace and synchronize the directory entry. The in-memory balance, profit and trade count change only after this durable commit. Reset uses the same transaction. Failed writes, file synchronization and replacement leave the previous account bytes and in-memory values unchanged; the implementation never removes the destination to retry a failed rename. Existing files named `<statePath>.tmp` are not reused or deleted.

If directory synchronization fails after replacement, Sentum attempts to restore the previous file and synchronize that restoration. If either recovery operation fails, `PaperAccount::PersistenceError::state_uncertain()` is true and that account instance rejects subsequent reads and changes. Stop the runtime, reconcile the configured file with the previous file named in the error when one was retained, and resolve the storage failure before restarting. The uncertainty latch belongs to the current process; restarting does not itself prove that reconciliation happened. Temporary files left by interrupted work are not automatically used to restore or reset an account, and files from other transactions are not removed during cleanup.

A persistence failure during runtime accounting, a strategy change or final settlement is reported as an error after all runtime workers have shut down and results in a nonzero process exit status. It is never reported as a successful account save.

Completed simulated trades also have a separate history finalization contract. Before submitting a simulated exit, the trader reserves the SQLite history writer with a five-second busy budget. A confirmed close receives an immutable identity and is recorded in a recovery journal before its history row is committed. A persistence failure halts further trading, retains the confirmed closed position and its accounting once, and is reported after worker cleanup. On reopening, recorded closes are transferred into history idempotently. Keep the history database and its `.trade-finalizations.sqlite3` companion together; see [Trade finalization and recovery](TRADE_FINALIZATION_RECOVERY.md) for failure states and the account-reconciliation boundary.

## Promoted models

`paper.modelDefinition` may point to a registered model definition. Sentum requires that model to have reached the `paper` promotion stage in `log/models.sqlite3`; otherwise startup fails closed. When accepted, the model supplies its strategy, symbol and risk-configuration path.

## Market data shown in the console

The scanner watchlist is derived from Sentum's in-memory market store and scanner state. The Market view may display spread-derived bid/ask estimates from the simulation model; these are explicitly simulation values and are not presented as an exchange Level-2 order book.

## Safety properties

Paper mode uses live public market data and simulated fills only. Pausing blocks new entries but never leaves an open position unmanaged. Manual closes pass through the normal simulated execution path, including configured fees, spread and slippage. Production exchange execution is not enabled by the terminal UI.
